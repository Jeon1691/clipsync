# OpenSSF Best Practices: Silver and Gold

Reviewed on **2026-11-15** against the official [Silver](https://www.bestpractices.dev/en/criteria/1?details=true&rationale=true) and [Gold](https://www.bestpractices.dev/en/criteria/2?details=true&rationale=true) criteria. This register covers all **55 Silver** and **23 Gold** criteria, including shared criteria at their stronger level. The [public project entry](https://www.bestpractices.dev/en/projects/16709) is authoritative for earned badges. The dynamic README badge shows the highest level actually earned; consult the public entry for the current award. Gold is not claimed.

The answers below describe the intended assessment of the published changes and their evidence. A configured check is not proof that its target was met. Unmet optional criteria include the reason; mandatory gaps cannot be waived by prose, bots or AI review. Source snapshots and current CI/release results should be checked before changing any answer.

## Required work that remains

- **People:** a second capable maintainer, an unrelated substantial contributor, and genuine pre-release second-human review of at least half of modifications are still needed for Gold. The owner separately confirmed an actual custodian/access/right/recovery arrangement meeting the one-week continuity requirement; it does not create a second developer.
- **Testing:** actual hosted Linux and macOS product coverage meets the 90% line/region and 80% branch Gold gates across all twelve product crates. Linux measures 95.18%/90.96%/85.60%; macOS 94.04%/90.35%/84.44% at c335d3c. The complete ledger registers 86/136 defects (63.24%) with a separate 50% gate. Platform-specific denominators are not combined; only test code is excluded.
- **Reproducibility:** Gold evidence must compare all six outputs and native-package manifests across two independently reconstructed frozen environments. The hosted reconstruction workflow and its source-bound artifacts establish this scope; local single-container diagnostics alone do not. The v0.2.0 relay transport fails closed until TLS is configured or plaintext HTTP is deliberately enabled; deployment migration is documented.
The maintainer confirmed an internal human security/design review of PR #16 on 2026-11-15; its revision, scope and limitations are recorded in the assurance case. This does not satisfy the separate two-person change-review requirement.

Optional work includes a project-wide DCO/CLA authority process, internationalization, complete accessibility verification and payload algorithm agility. Current compatibility/security limits are recorded rather than hidden. The solo owner's cryptographic 2FA use was confirmed on 2026-11-15; no recovery codes or authentication secrets are stored here.
